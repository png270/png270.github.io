How to catch bugs online (fast)?

Catching bugs requires different tools and techniques depending on whether you are targeting flying insects, crawling ground-dwellers, or source code.

Published: August 28, 2026 • By: Siddhi

I was once doom scrolling on Twitter (*I don’t like to call it X yet) and came across a piece of code published by Bug Crowd as part of their “Spot the Bug” series. It asked to spot a potential vulnerability in the code snippet and I failed miserably. Not because I didn’t know how to read code, but because I failed to stop at every line and think about it. Think about how the data flows, what happens to it at that specific line of code and what could I modify as an attacker to exploit something. This is a game of patience and practice.

Secure code review feels more like an art to me than a deliberate examination process designed to catch bugs in code. Mind you, there’s a big difference between a bug and a vulnerability. Bugs are functional flaws while vulnerabilities are flaws that create security weaknesses that an attacker can exploit. All vulnerabilities are bugs, but not all bugs are vulnerabilities, by the way. For example, a typo misaligning a UI element is a bug and poses no security risk. So, you may ask why do we need secure code review in the first place? There are SAST tools that can scan your code and find you pain points as well as functional testing that takes place.

What’s the big deal then? First, it helps you find flaws that functional testing and automated code scanning misses. The guesses an attacker can make cannot be replicated by an automated approach in certain cases. And second, its’s a huge cost saver because it’s way cheaper to fix them during development than fix the vulnerabilities after your application has been breached. And finally, there’s no harm in learning the skill lol.

Unfortunately, there aren’t many sources for secure code review that can help you learn the skill or provide a specific framework to do so. So, here’s my approach on how I’m learning the skill and how I’m trying to get better at it.

Ever heard of an LLM called ChatGPT? Of course. I asked GPT to give me a code snippet every day for secure code review practice and then grade my responses. Initially, I found it difficult it to understand what is happening in the code because my first instinct was to catch that one line of code which has the vulnerability. However, after my first few failed attempts, I understood how important it is to learn how to read code. Reading code essentially means understanding where the input is coming from, how the data flows and the result it is trying to accomplish.

The next thing I kept fumbling at was classifying the vulnerabilities. I found everything to be a problem created by missing input validation and sanitization. It was a recurring answer but not every vulnerability is caused by user input. So, I asked the LLM to help me not do that. *It feels really weird to say it out aloud how I’m being taught a skill by an LLM.* Here’s the approach it spit out –

“Use the following framework to structure your answer – Finding → Evidence → Impact → Fix.”

It worked in improving my answers. But I still wasn’t there at accurately classifying the vulnerabilities. I got over blaming user inputs so that was a win.

Another thing I realized was how badly I needed to understand how common vulnerabilities worked. While I could identify what line of code is problematic and how an attacker can manipulate it, I’m still far from naming it correctly. There have been multiple hits and misses with this approach.

For example, for this code snippet which includes a Python endpoint that restores UI preferences from a browser cookie, my approach resulted in correctly identifying the vulnerability. I described it as -

“source is a cookie, sink is preferences = pickle.loads(raw). Missing control is -unauthenticated cookie, untrusted cookie. If pickle deserialized malicious cookie, it can result in arbitrary code execution”

What I missed was naming the vulnerability correctly which was “Insecure deserialization”. A good fix is to never deserialize untrusted pickle data. Using a non-executable format such as JSON, validating it against a strict schema, and using a signed cookie are good ways to mitigate it. However, I couldn’t figure this fix out so it went into my database/table. Yes, I created a tracker that would include a vulnerability name, the root cause and a fix. This is good for recall but there’s a long way to go for me to be an expert at it.

python 

import base64
import pickle
from flask import Flask, request, jsonify

app = Flask(__name__)

@app.get("/api/preferences")
def get_preferences():
encoded = request.cookies.get("preferences")

    if not encoded:
        return jsonify({
            "theme": "light",
            "language": "en"
            })

        raw = base64.b64decode(encoded)
        preferences = pickle.loads(raw)

        return jsonify(preferences)

Here’s another example where I felt like I correctly evaluated the code but missed the key vulnerability.

python 

@app.get("/api/admin/users/export")
@require_admin
def export_users():
    users = db.users.find_all()

    output = io.StringIO()
    writer = csv.writer(output)
    writer.writerow(["Name", "Email", "Company"])

    for user in users:
        writer.writerow([
            user.display_name,
            user.email,
            user.company_name
        ])

    return Response(
        output.getvalue(),
        mimetype="text/csv",
        headers={
            "Content-Disposition": "attachment; filename=users.csv"
        }
    )

My answer this time was -

“Program flow + inputs = no inputs passed, finds all users in the db, the output is given as a string. A writer is created to write the output to a csv file. creates rows with name, email and company. now the resulting query stored in users is parsed to write name, email, company. Then the output is produced as a csv and headers are updated. given - users can edit their own name and company name. The export is opened in spreadsheet software.

My first assumption is that the headers are being returned. If content-disposition header is modified, file name is changed to some other pe, a malicious file can be downloaded. This is a vulnerability, maybe a HTTP header poisoning/injection vulnerability more like stored XSS, so if one user who exports the file can change extension, maybe add malicious code init. when a legit user exports and views the file, it'll misbehave. Ideal fix could be maybe use encoding for filenames?

oh this also makes me realize, a malicious user can try putting full paths in the filename and it can lead to path traversal vulnerability. encoding it properly might help, i guess. I'm not sure.”

3/10 for the attempt. I described the program flow accurately, but I focused on a value that the attacker does not control. I also overlooked the stored user-controlled fields. Simple, yet deceiving.

I now try to lay out my understanding of the code first, summarize what it does and how the input flows around. Then I try to identify everything an attacker might try to influence for example, request body and route/query parameters, headers and cookies, uploaded filenames and content, database values originally submitted by users, webhook events, URLs and redirects, configuration supplied by another system etc.

Another thing I check for is trust. Is the caller authenticated? Is this specific action authorized? Does the requested object belong to this caller? Can the caller assign privileged fields? Is the request genuinely from the claimed system? Is the data merely syntactically valid, or is it also permitted?

This helped me identify where the potential problem is. However, I still at times don’t understand where the fix could be applied. Knowing where the problem is one thing but to know how to fix it correctly is a whole new but also very related task.

What helped me get better at this point was reading up on common vulnerabilities and creating a table of fixes that can be applied to fix it.

I’m still practicing but some other resources I’ve found to be extremely helpful are –

  • Reading source code of vulnerable applications. OWASP Juice Shop or DVWA are some good open-source vulnerable application that can be found on GitHub. Or just looking at OWASP Secure Code Review cheat sheet can also give you a good start at how to approach it.
  • Another great guide is on Medium. This medium article clearly describes what you should do to learn secure code review. There’s a GitHub repository as well as YouTube walkthroughs by the author that should be given a good consideration.
  • Finally, PentesterLab has a great introduction and a lab exercise full of code files that can help with practice.
